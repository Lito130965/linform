# Security

## Reporting a vulnerability

Report privately through GitHub's [security advisory
form](https://github.com/Lito130965/linform/security/advisories/new), or by
opening an issue that says only "security issue, please make contact" with no
detail. Please do not put a working exploit in a public issue.

There is no bounty and no SLA — this is a single-maintainer project. Reports
are read, and anything that turns out to be real gets fixed and credited in the
changelog unless you prefer otherwise.

## Threat model

Two sentences carry most of it:

**A template is untrusted code.** Templates are written by users, imported from
Word documents, and generated by an AI assistant, and they are then executed by
a template engine and a rendering engine. They are treated accordingly: Jinja
runs sandboxed, external URL fetching is off by default so a template cannot
make the *server* fetch internal addresses, and markup is stripped of
executable content before it reaches the editor's canvas, with a
Content-Security-Policy behind that.

**An editor user is trusted.** Anyone who can sign in as an editor can write a
template, upload an asset and see every template in the deployment. There is no
per-template permission model and no separation between editors. If that does
not match your situation, run separate instances.

### What is covered

| Area | Treatment |
|---|---|
| Template injection (SSTI) | Jinja sandbox; attribute traversal and dangerous builtins refused. Tested. |
| Server-side request forgery | Only `data:` URIs by default; `http(s)` requires an opt-in plus a host allowlist. `file://` never. |
| Script execution in the editor | Input sanitised before it reaches the same-origin canvas; CSP with `script-src 'self'` behind it. |
| Uploaded files | Served from a content hash; anything outside a safe MIME allowlist is sent as an attachment, so an uploaded SVG cannot run when opened directly. |
| Credential brute force | Per-account lockout checked *before* the password hash is computed (which also makes it a CPU-exhaustion guard), plus a per-address rate limit. Uniform 401 so the endpoint is not an account enumerator. |
| Secrets at rest | Passwords are PBKDF2-hashed; session tokens and API keys are stored as SHA-256 digests. A clear API key is shown once, at creation. |
| Business data | Payloads are rendered and forgotten — never persisted, never logged. |
| Denial of service by load | Hard render timeout and a hard in-flight ceiling; excess is refused with `429`, not queued. |

### What is not covered

Stated plainly, because an unlisted gap reads as an overlooked one:

- **No deployment role split yet.** Every instance mounts the management API as
  well as the render API. A render-only token cannot change templates, but the
  endpoints are still there. Until that is separated, keep the editor on an
  internal network.
- **No per-template or per-directory permissions.** Directories are
  organisational only.
- **No audit log.** Version authorship is recorded; who *read* what is not.
- **Session tokens live in `localStorage`**, which is a deliberate trade: it
  keeps the API a plain Bearer interface with no CSRF surface. It is sound only
  because script execution in the editor origin is prevented by sanitisation
  and CSP — the two are one decision, not two.
- **No rate limiting on rendering per caller.** The in-flight ceiling protects
  the instance, not one tenant from another.
- **Assets are served without authentication by default.** The 64-hex content
  hash is an unguessable capability URL; a browser cannot send headers on an
  `<img src>`. Set `LINFORM_ASSETS_REQUIRE_AUTH` when that trade is wrong for
  you — *(planned; not yet implemented)*.

## Hardening checklist for a deployment

1. Set `LINFORM_SUPERUSER` / `LINFORM_SUPERUSER_PASSWORD`, or at minimum the
   static tokens. Without either, **authentication is off**.
2. Give consuming applications a **render** key, never the admin token.
3. Terminate TLS in front of the service; it speaks plain HTTP.
4. Keep the editor off the public internet until the role split lands.
5. Leave `LINFORM_ALLOW_EXTERNAL_URLS` off unless you need it, and pin
   `LINFORM_ALLOWED_URL_HOSTS` when you do.
6. Back up the database — it holds the templates *and* the assets.

## Reading a dependency advisory

`pip-audit` and `npm audit` run on every build. The frontend report needs one
distinction before it can be acted on, because without it the numbers are
alarming and mostly irrelevant.

**What ships is `dist/`** — static files produced by `vite build`, plus the
Python service. Vite, Vitest and esbuild are devDependencies: they are not in
the image, and the advisories against them describe a *running dev server* or
the Vitest UI server. Neither exists in a deployment, and neither is started by
CI, which runs `vitest run` and `vite build`. They still deserve upgrading —
a contributor running `npm run dev` is a real machine — but they are not a
property of your installation.

**What does reach a browser** is the runtime side of `frontend/package.json`:
React, CodeMirror, markdown-it, and mammoth (with its `underscore`) which parses
`.docx` files an editor uploads. An advisory there is executed by a real user on
real input, and is the kind worth acting on the day it appears.

CI encodes exactly that split: `npm audit --omit=dev` is **blocking**, and the
full audit is advisory. So a vulnerability in what you deploy fails a pull
request, and one in a build tool is visible without holding up unrelated work.
